# .ipynb vs Marimo (.py): что удобнее на этапе DevOps

Сравнение делал на маленьком сценарии (`marimo_example.py` рядом): загрузка Wine, базовая статистика, пара SQL-запросов через duckdb. Выводы по пунктам.

## 1. Воспроизводимость и hidden state

- **Jupyter/Colab**: ячейки запускаются вручную в любом порядке. Переменная, удаленная из ячейки выше, остается в kernel и продолжает работать. Через 20 минут работы получаешь "у меня работает", у коллеги после `Restart & Run All` - ошибка.
- **Marimo**: граф зависимостей между ячейками вычисляется статически. Удалил переменную - все зависимые ячейки автоматически инвалидируются. Hidden state физически невозможен.

## 2. Версионирование в git

- `.ipynb` - JSON с base64-кодированными outputs, метаданными kernel и счетчиками `execution_count`. Каждое перезапуск ячейки меняет файл, даже если код не трогал. PR-диффы нечитаемы без `nbdime`/`jupytext`.
- `.py` Marimo - обычный Python-файл с декораторами `@app.cell`. Diff = реальные изменения кода. Code review проходит как для любого другого .py.

## 3. CI/CD

- Запуск `.ipynb` в pipeline - `papermill`/`nbconvert`/`jupyter nbconvert --to notebook --execute`. Лишние зависимости, медленный старт kernel, фейлы на pickled outputs.
- Marimo: `python notebooks/marimo_example.py` - ноутбук работает как обычный скрипт (есть entrypoint `app.run()`). Тестируется через pytest, импортируется как модуль, прогоняется через любой CI runner без кастомных шагов.

## 4. Колаб-специфичные ограничения

- VM эфемерная: после disconnect все `!pip install` сбрасываются. Нет lockfile, нет фиксированного образа, версии зависимостей плывут между запусками.
- `!pip install` зашит прямо в ячейках - это не requirements.txt, его не подцепит `pip install -r`. Воспроизвести среду на CI или у коллеги одной командой нельзя.
- Привязка к Google Drive для данных - значит данные не лежат в DVC/S3, а в чьей-то личной папке. Несовместимо с командной разработкой и DataOps.
- Нет нативного интегрирования с git: коммиты делаются "руками" через GitHub-плагин, история обычно теряется.

## 5. Интеграция с MLOps-стеком

- DVC pipeline через `dvc.yaml` хочет команду вида `python src/train.py`. С `.ipynb` это `papermill notebook.ipynb out.ipynb -p ...` - один лишний слой и кэширование DVC ломается на изменении output-метаданных, хотя реальный код не менялся.
- Marimo `.py` ложится в `dvc.yaml` напрямую как любой скрипт. Хеш стадии стабильный.
- `mlflow.log_artifact` для `.py` - просто файл; для `.ipynb` это 12+ MB JSON с outputs (как исходный `HW5_MLOps.ipynb` в этой папке - 11.8 MB только за счет картинок в outputs).

## Вывод

На этапе DevOps Marimo выигрывает по всем пунктам жизненного цикла: code review, версионирование, CI/CD, упаковка артефакта. Jupyter/Colab остается удобен для интерактивного исследования и презентаций, но в production-pipeline его место - либо после конвертации в `.py` через jupytext, либо через papermill с осознанной ценой обслуживания.
