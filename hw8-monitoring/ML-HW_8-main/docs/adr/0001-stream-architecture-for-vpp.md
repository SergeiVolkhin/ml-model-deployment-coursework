# ADR 0001 - Kappa-архитектура для Virtual Product Placement

Дата: 2026-05-16
Статус: принято

## Контекст

Сервис Virtual Product Placement (VPP) подменяет логотипы и продакт-плейсмент в кадре видео онлайн-кинотеатра в реальном времени для каждого зрителя индивидуально. Входной поток - бесконечный (живой видеоконтент и каталог), выходной поток - бесконечный (плеер каждого зрителя), нагрузка - до 10 000 RPS на инференс-сервис в пик.

Ключевые свойства задачи:
- Видеокадры приходят непрерывно, понятие "батча" искусственное.
- Любая задержка > 200 мс на кадр ломает UX (плеер начинает буферизовать).
- Каталог брендов и профили зрителей меняются часто, но не критично для отдельного кадра.
- Retrain моделей запускается дискретно, на накопленных данных, но шаг 1-7 дней - не быстрее.

## Альтернативы

### A. Lambda (стрим + батч-слой параллельно)

Lambda держит два пайплайна: real-time (Spark Streaming / Flink) и батч (Spark batch). Real-time даёт быстрые приближённые ответы, батч - корректирующие точные. Плюсы: устойчивость к bug в стриме (батч переиграет). Минусы: дублирование кода и инфры, два набора алертов, два метрик-стека, два момента согласования схемы. Для VPP батч-слой бесполезен - подменять логотипы постфактум нельзя.

### B. Kappa (только стрим, переигрывание через replay)

Один пайплайн (Kafka + Spark Structured Streaming или Flink), все ретроспективные расчёты делаются переигрыванием kafka-топика. Retrain - отдельный orchestrator, который читает тот же исторический топик. Плюсы: единый код, единый мониторинг, проще согласование схемы. Минусы: kafka retention должен покрывать максимальное окно retrain (обычно 14 дней).

### C. Микро-сервисы без шины (gRPC fan-out)

CDN -> service A -> service B напрямую, без kafka. Плюсы: меньше задержка на хоп. Минусы: нет естественной возможности replay для retrain; невозможно горизонтально масштабировать independent consumer'ов; отказ одного сервиса валит весь поток.

## Решение

Выбрана Kappa-архитектура (B). Все события движутся через Kafka (`video_frames_raw` -> Spark Structured Streaming -> `video_frames_enriched`), retention 21 день покрывает максимальное окно retrain (14 дней) с запасом. Discriminative AI (YOLO + segmentation) и Generative AI (inpainting) подключены к стриму как независимые consumer-группы, что позволяет масштабировать их раздельно.

## Последствия

Положительные:
- Один пайплайн = один набор инфры, метрик и алертов. Меньше когнитивной нагрузки на команду.
- Retrain тривиален - запускается на том же kafka-топике с offset reset.
- Идемпотентность достигается через event-time semantics в Structured Streaming (exactly-once на sink).
- A/B-эксперименты легко включаются как дополнительные consumer-группы.

Отрицательные / риски:
- Kafka retention (21 день) требует значительного дискового бюджета на брокеры.
- При багах в моделях нельзя "переиграть" постфактум - запорченные кадры уже доставлены зрителю.
- Latency-бюджет в стриме строже, чем при микс-Lambda - все сервисы должны держать p95 < 200 мс на свой шаг.

Митигации:
- Tier'ный retention в kafka: 21 день для raw, 24 часа для enriched.
- Shadow deployments новых моделей через отдельный consumer-group перед промоушеном в prod.
- Прометей-алерт на p95 latency каждого шага стрима, отдельный SLO per-stage.
